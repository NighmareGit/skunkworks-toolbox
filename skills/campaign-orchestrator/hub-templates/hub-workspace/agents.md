## Workspace Purpose

This folder is the **orchestration nerve center**: the hub from which we work on projects.

- **Hub machinery (user-level, any session):** `{{GROK_HOME}}/` — agent type definitions (`agents/*.md`), role registry + architecture (`ROLE-REGISTRY.md`, `ROLE-ARCHITECTURE.md`), role prompts (`prompts/`), workflows (`workflows/*.rhai`), skills (`skills/campaign-orchestrator/` with the portable toolchain bundle).
- **Project state (project-scoped):** each project keeps its own `.scratch/` — working toolchain copies (`toolchain.py` + the `tool_*.py` modules, `dispatch-state.py`, …), the dispatch-brief registry, the state machine, `DECISIONS.md`, `RESUME.md`. The hub never holds project campaign state.
- **Project registry:** `config/projects.yaml` maps project names → paths.

## Session Startup (hub session)

Do these IN ORDER:

1. **Read this file** — you're here.
2. **Scan the hub:** run `python3 {{GROK_HOME}}/skills/campaign-orchestrator/scripts/hub-scan.py` — lists every project with campaign state + its next action. This is your "what's happening" readout.
3. **If a `RESUME.md` exists in a project** (`.scratch/task-state/RESUME.md`): that project was handed off — a previous session left the exact resume command + memo. Follow it (a fresh session needs no other instruction; the human only said "resume").
4. **To work on a project:** target it with `--cwd`, or `cd` into it and read its `agents.md` (canonical per-project conventions). Every toolchain command resolves against `--cwd`, so the hub needs no cd-ing:
   ```bash
   .scratch/scripts/dispatch-state.py next-action --cwd {{PROJECTS_ROOT}}/<project>
   .scratch/scripts/toolchain.py dispatch --mode handoff --cwd {{PROJECTS_ROOT}}/<project>
   ```
   (from the hub, use the bundled copies: `{{GROK_HOME}}/skills/campaign-orchestrator/scripts/toolchain/…` — identical to a project's copies).
5. **Report status to the user** before acting: what's active, per project, and the recommended next action.

## Loading a Project by Name ("read agents.md from project xyz")

When the user says *"read agents.md from project xyz"* (or "work on xyz"), resolve the
name in this order, then read that project's `agents.md` and operate with `--cwd`:

1. **Registry:** `config/projects.yaml` → `name:` → `path:` + `agents_md:`.
2. **Convention:** `<projects-root>/<name>/agents.md` (default root `{{PROJECTS_ROOT}}/`).
3. **Verify + status:** `hub-scan.py --project <name>` prints path, agents.md, and the
   project's next action — run it, then read the file it points to.

This is *discovery, not pollution*: the hub knows HOW to find a project (registry +
convention), never hardcodes WHICH projects must exist. Adding a project is one line in
the registry — or nothing at all if it lives under `{{PROJECTS_ROOT}}/`.

```bash
python3 {{GROK_HOME}}/skills/campaign-orchestrator/scripts/hub-scan.py --project <project>
# → path + agents.md + next action; then read that agents.md, operate with --cwd
```

## Session Handoff ("we need a new session")

Trigger: the user says a new session is needed / hand over / handoff / takeover.

For EVERY project with campaign state, run (one command each):
```bash
{{GROK_HOME}}/skills/campaign-orchestrator/scripts/toolchain/toolchain.py \
    dispatch --mode handoff --cwd <project> --note "what I did, what's next"
```
It settles the mechanical state, stamps `DECISIONS.md`, writes that project's `RESUME.md` (exact resume command + your memo), and prints what the fresh session will do on boot. Then "resume" is all the fresh session needs per project.

Wrong-directory guard: a handoff against a dir with no campaign state FAILS loudly — it never silently "hands off" nothing.

## The Dispatch Spine (how campaign work actually flows)

- **State machine (stateless interpreter):** `dispatch-state.py` — files ARE the state. `next-action` computes THE next command from files alone (VERIFY in-flight → DISPATCH ready → ADVANCE verified → RECOVER failed). Stop anywhere, boot anywhere, same trajectory.
- **Lineage:** every dispatch carries a `dc_<uuidv7>` DISPATCH_ID persisted in the brief registry (`dispatch-trace.py` mint/link/trace/locate).
- **Dispatch wrapper:** `toolchain.py dispatch` modes — `pre` (mint + brief + checks), `post` (file-output verification), `post-workflow` (structured workflow results: link agent ids + transitions + decision log), `handoff` (one-command session handover), `sabotage` (failure-injection gates), `pivot`-is-now-`handoff`.
- **Workflow-first waves:** `{{GROK_HOME}}/workflows/dispatch-wave.rhai` — dispatch a fan-out via `agent_type` (the type registry), cross-model verification panel (`verifier` type), per-result linkage, `artifact_path` for implementer deliverables.
- **Consistency gates:** `config-consistency.py` (D1/D2/D2b/D2c — registry, definitions parse + match, workflow `agent_type` refs), `arch-validator.py`, the 94-test suite, sabotage 8/8.

## Orchestrator Delegation Rule

When acting as orchestrator, **never execute task work directly**. Dispatch sub-agents (per `{{GROK_HOME}}/ROLE-REGISTRY.md` type table) for execution, planning, and review. Retain verification + recovery + decision logging.

## Lessons Learned & Cross-Project Knowledge

- **Bash foot-guns:** `x=$(failing)` kills under `set -e` → use `|| rc=$?`; `((x++))` is falsy when x=0 → use `$((x+1))`. `grep -c` prints `0` AND exits 1 on no match → `|| true` not `|| echo 0`.
- **YAML front-matter trap:** an unquoted `: ` (colon-space) inside a description scalar breaks the agent-definition parse (serde_yaml) and SILENTLY drops the type from discovery ("Unknown subagent type"). Quote descriptions. `config-consistency.py` D2b now catches this.
- **User-scope types can't shadow builtins** (`plan`, `explore`, `general-purpose`) — that's why the planning type is `planner`. Verified in discovery.rs.
- **`validate_only` doesn't exercise live type resolution** — the live run is the real proof.
- **Cross-platform:** scripts use `pathlib.Path`; shell commands documented for bash. Legacy Windows/WSL notes: `docs/grok-cli-linux-wsl-guide.md`.

## Emergency Stop

To pause any campaign immediately:
1. Note the current task ID and agent ID.
2. Kill the sub-agent process (if identifiable).
3. Set the task `status: failed`, `needs_resume: true` (or transition the dispatch to `failed`).
4. Log the pause in that project's `DECISIONS.md` with rationale.
5. Run `dispatch-state.py status --cwd <project>` to confirm state.
